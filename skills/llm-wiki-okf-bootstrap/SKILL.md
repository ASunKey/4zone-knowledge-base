# LLM Wiki (OKF) 知识库脚手架

在两个方法论上搭建可被 LLM 维护、可被人类浏览、可跨工具交换的 markdown 知识库：

| 方法论 | 来源 | 提供 |
|---|---|---|
| **LLM Wiki** | Karpathy gist `442a6bf555914893e9891c11519de94f` | 三层架构（raw / wiki / schema）、Ingest/Query/Lint、index.md + log.md |
| **Open Knowledge Format (OKF)** | `github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf` | 一概念一文件、YAML frontmatter、保留文件名、跨链接、宽松一致性 |

## STEP 0 — 先看有没有现成样板

如果你手头已有遵循四区模式的知识库，**先 `ls` 参考样板**，复制其 `AGENTS.md` 结构与约定，再按新主题改写。不要重新发明。

```bash
ls "<参考样板目录>/"
find "<工作区>" -maxdepth 4 -iname "okf*" -o -maxdepth 4 -iname "*lint*.py"
```

## STEP 1 — 目录骨架

```
<Project>/
├── AGENTS.md      ← Schema（核心！人机共建）
├── README.md      ← 人类入口
├── okf.yaml       ← OKF 配置（profile: <project>-v1）
├── index.md       ← 内容目录（OKF 保留名）
├── log.md         ← 变更日志（OKF 保留名，append-only）
├── raw/           ← 区一：外部来源，不可变
│   ├── index.md  reports/  articles/  policies/  cases/  data/  assets/
├── reflections/   ← 区二：思考沙盒（按指令落盘，不自动写）
│   └── index.md
├── results/       ← 区三：Compile 产出（交付即定稿）
│   └── index.md
├── wiki/          ← 区四：OKF bundle，LLM 完全拥有
│   ├── index.md  overview.md
│   ├── domains/<域1..域N>/index.md
│   ├── concepts/  entities/  methods/  metrics/  synthesis/
└── scripts/       ← 零依赖工具（见 STEP 4）
```

> **`raw/` 的每个子目录都要有 `index.md`**，否则目录链接在 lint 里会报坏链。

## STEP 2 — OKF frontmatter 规范

**唯一必填字段是 `type`。** 推荐 `title` / `description` / `resource` / `tags` / `timestamp`。

```yaml
---
type: concept              # 必填，非空
title: "概念名"
description: "单句摘要（用于 index 生成与检索片段）"
resource: https://...      # 底层资产 URI；抽象概念可省
tags: [a, b]
domain: <域slug>            # 本库扩展
sources:                    # 本库扩展：raw 层路径
  - raw/articles/xxx.md
related:                    # 本库扩展：显式 wiki 关联
  - wiki/concepts/yyy.md
confidence: medium          # 本库扩展：high/medium/low —— 证据强度诚实标注
status: seed                # 本库扩展：seed/growing/stable/stale
timestamp: 2026-09-25T22:30:00+08:00
---
```

**一致性判定**：每个非保留 `.md` 有可解析 frontmatter + 非空 `type`。

**版本提示**：博客公开的是 v0.1；spec 仓库已是 v0.2 draft，含 breaking change
（`timestamp`→`generated.at`、正文 `# Citations`→`sources` frontmatter）。
**稳妥做法 = v0.1 核心 + v0.2 前瞻扩展**（OKF 允许任意扩展键，消费者须容忍未知字段）。

**保留文件名**：`index.md`、`log.md`（不得作为概念文档）+ `AGENTS.md`、`okf.yaml`（本库约定）。

## STEP 3 — 写 AGENTS.md（最重要的一步）

Karpathy 原话：schema 是"让 LLM 成为有纪律的 wiki 维护者、而非通用聊天机器人的关键配置文件"。

必含小节：
1. **项目定位 + 明确不做什么**
2. **四区模式架构图**（含 Karpathy 三层 → 四区的映射表）
3. **OKF 合规规范**（字段表 / 一致性判定 / 保留名 / 交叉引用规则 / 正文约定）
4. **知识域体系**（每域：核心命题 / 关键议题 / 代表玩家 / 前沿观察）
5. **操作工作流**：Ingest（阅读→归档→摘要→交叉引用→索引→日志→矛盾检查）/ Query / Lint
6. **页面模板**（概念 / 实体 / 方法 / 指标）
7. **约定与偏好**（见下）
8. **`.kb/` 项目数据目录约定**

### 关键约定

- **文件名用 kebab-case ASCII slug**（`example-entity.md`），**标题正文用中文** —— 跨平台（Windows↔macOS↔Linux）同步安全，避免 NFC/NFD 冲突
- **交叉引用用包根绝对路径** `[文本](/wiki/entities/example-entity.md)` —— 文件移动后仍稳定
- **双源并列原则**：数据冲突时**不合并、不取平均**，两处都写并标注口径差异
- **凡数字必附 `sources`**
- **`confidence` 诚实标注**：不确定标 `low/medium`，并在「争议与不确定性」小节说明**缺什么**
- **reflections 不自动落盘** —— 仅用户明确指令才写

## STEP 4 — 三个工具脚本（纯标准库，零依赖）

不要引入 PyYAML / qmd（`~100 源以内 index.md 已够导航，Karpathy 原话`）。
每个脚本内联一个**极简 frontmatter 解析器**（~30 行），避免依赖。

### `okf_lint.py`
检查：OKF 合规 / 坏链 / 孤儿页 / 保留文件名 / domain 合法性 / confidence·status 分布。
退出码 0=PASS、1=FAIL。支持 `--quiet` `--todo`。

### `build_index.py`
扫描 frontmatter 重建 `wiki/index.md` + 统计表。支持 `--write` `--stats` `--json`。

### `wiki_search.py`
加权本地检索：`title×10 / tags×6 / desc×4 / body×1`（上限 5）+ 词组命中 ×5。
支持 `--tag` `--domain` `--type` `--list-types`。

## STEP 5 — 踩坑记录（血泪教训，务必照做）

### 坑 1：lint 必须剥离代码块再提取链接
文档里的示例链接（如 `[邻居](./other.md)`）会被误报为坏链。

```python
INLINE_CODE_RE = re.compile(r"`[^`\n]*`")

def strip_code_fences(text):
    out, in_fence = [], False
    for line in text.split("\n"):
        if line.lstrip().startswith("```"):
            in_fence = not in_fence
            continue
        if not in_fence:
            out.append(line)
    return INLINE_CODE_RE.sub("", "\n".join(out))
```

### 坑 2：目录链接应视为有效
`[reports/](reports/)` 指向目录，目录存在即有效，不要报坏链。

```python
if resolved.is_file():
    ...
elif resolved.is_dir():
    outbound[r].add(rp + "/")   # 目录链接有效
else:
    broken[r].append(target)
```

### 坑 3：build_index 不能无条件跳过 `index.md`
域索引页（`type: domain_index`）虽然名为 `index.md`，但**承载实质内容**，应当收录。
只跳过 `type: index` 的纯目录文件。

```python
if p.name == "index.md" and str(meta.get("type","")).strip() == "index":
    continue
```

### 坑 4：frontmatter 解析器的边界
- `timestamp: 2026-09-25T22:30:00+08:00` 含冒号 → 用 `partition(":")` 只切第一个
- `key:` 后跟 `  - item` 块列表 → 需 `cur_key` 状态跟踪
- `tags: [a, b]` 行内列表 → 检测 `[` `]` 包裹
- 值要 `unquote`（剥掉配对的 `"` `'`）

### 坑 5：链接检查要跳过外链与锚点
`http://` `https://` `mailto:` `#` 开头的一律跳过。

### 坑 6：python 解释器用系统默认或显式声明
```bash
python3 scripts/okf_lint.py
# 或显式指定解释器（路径随系统而定，勿写死绝对路径）
```

### 坑 7：同一对象的数字在「媒体 vs 官方门户」之间会系统性偏差
实测规律：**媒体转述的数字普遍高于官方门户网站，且随年份推移同步上调**，
原因通常是**口径滚动更新但未统一发布**（例：同一对象某年收入出现两个值；游客数出现两个值；
传播范围出现「X 多个」/「Y 多个」两值，而两个来源相差仅数月）。

**处理方式**：
- **并列保留全部数值并标注来源与日期**，绝不择一、不取平均；
- 在索引中总结为一条**通用规律**（「媒体 > 官方门户，逐年上调」），提醒后续引用者；
- 在文件顶部写 `⚠️ 使用本案例数据时必须标注来源与日期`。

### 坑 8：PDF 提取稿的日期/数字错误要如实标注，不静默修正
实测：某 PDF 版把某年份写错（如把 2017 写成 2004）。
**处理方式**：采信通行正确值，同时在「争议与不确定性」中**显式记录该异常并说明可能是 OCR/原文错误** ——
不要静默改掉（静默修正会让读者无法判断来源可信度）。

### 坑 9：母体制度页不是可选项
做「同一母体的 N 种路径」类子区时，若跳过「母体制度页」直接写各对象，
读者无法理解**为什么这些对象共享同一批素材**，横向对比失去合法性。见 STEP 8.6 ①。

### 坑 10：涉台港澳的表述必须逐处转换
采集资料时来源原文常写「台湾地区」「台青」「金门」等。
**本库自身表述**须统一为「中国台湾」「中国台湾地区」；**历史文献名**（《续修台湾府志》）原样保留；
金门按国家立场表述为**中国福建省金门县**。**必须在 AGENTS.md 第 7 节固化此规则**，否则后续会话会漂移。见 STEP 8.6。

## STEP 8 — 多语种 raw 采集（用户要求多语言资料时）

### 目录结构

**可建多个专题采集区**（同一套机制复用）：如 `raw/methods/`（方法/怎么做）、`raw/regions/`（某地区的发展路径）。
**开新专题区前先定「议题框架」** —— 框架决定搜索词与文件切分。
（例：某地区专题可用 N 条主线：顶层设计 / 园区街区 / 历史资源活化 / 区域 IP / 目的地营销 / 政策资金 / 节庆活动 / 文化驱动再生。）

```
raw/<专题>/                   ← 专题采集区（每区一套语种子目录）
├── index.md                  ← 汇总（语种分布 / kind 分布 / 方法族聚类 / 核心张力 / 质量分级 / 补源优先级）
├── zh-CN/  (index.md + N 篇)  ← 中文笔记，保留原引用
├── zh-TW/  (index.md + N 篇)  ← 中文笔记，保留繁中原文
├── ja/     (index.md + N 篇)  ← 中日双语
├── en/     (index.md + N 篇)  ← 中英双语
└── bilingual/ (index.md + N 篇) ← 其他语种（ko/de/fr/id/es…）中 + 原语种对照
```

**新增专题区时的 Schema 改动（3 处，缺一不可）**：
1. `okf.yaml` → `types:` 新增该类型（如 `raw/regions: "某地区发展路径来源"`）
2. `AGENTS.md` → 架构图新增该目录块 + 第 7 节新增该区的采集规则与议题框架
3. `raw/index.md` → 子目录表 + 来源清单新增该区段落与篇数表

**每个子目录必须有 `index.md`**，否则目录链接报坏链（同 STEP 1 注）。顶层 `raw/index.md` 与
`raw/<专题>/index.md` 要做**双向导航**。

### frontmatter 扩展字段

```yaml
type: raw/<专题>      # 在 okf.yaml 的类型词表里新增这一项
lang: ja               # 源语种：zh-CN/zh-TW/ja/en/ko/de/fr/id/es…
kind: method           # content（内容/案例）| method（方法/流程）| both
```

### 双语对照格式（本库新规范）

**所有非中文来源一律产出「中文 + 原语种」段落级对照 MD**，格式统一为：

```markdown
> **原文（日本語）**
> 「自分なりの観察を重ねて設定した『問い』に対し、解決策を生み出していく一連の行為を『デザイン』と呼びます。」

> **中文对照**
> 「针对自己反复观察后设定的『问题』，去生成解决方案的一连串行为，称为『设计』。」
```

- 引用块交替（原文块 + 中文块）可读性最好；**表格用双语列**更紧凑（`| Original (EN) | 中文 |`）
- **原语种原文必须完整保留** —— 目的是可溯源、可复核译法，不要只给译文
- 术语保留原语种原词（métiers d'art / monozukuri / 민화），不要强行翻译

### 搜索策略（关键踩坑）

| 坑 | 现象 | 对策 |
|---|---|---|
| **通用引擎对日/韩关键词返回中英文结果** | 用 `文化IP デザイン 手法` 搜到的多为中文文章 | 用**母语原生表达**：`○○ ブランディング 成功要因`、`감성공학`、`문화콘텐츠 캐릭터 디자인 방법론` |
| **搜到的不是母语源** | 法语查询返回**英文撰写的法国题材文章** | **不要冒充母语源** —— 在文件内 `> 语言说明：…` 显式标注，`lang` 仍标 `fr` 但说明来源语言 |
| **中文源过多排挤小语种** | 小语种结果被中文二手汇编淹没 | 一次只搜一个语种，用该语种独有的实体名（品牌/机构/学者）作锚点 |
| **A 级来源缺失** | 抓到的多是 B/C 级媒体与咨询机构 | 在 index 里列**补源方向**（政策原文、官方统计、企业年报），不要假装齐备 |

### 交付前的跨语种整理（高价值动作）

1. **方法族聚类**：把不同语种里结构相似的方法归为同一「族」，在 `raw/<专题>/index.md` 列表
   （例：中文"四步法"、某语种"六阶段"、英文"某模型"同属"资源转译族"）
2. **寻找张力而非共识**：把来源之间**互相冲突**的主张单列（例：A 派「IP 人格必须精确」
   vs B 品牌「表情留白以最大化投射」）→ 作为待建 `wiki/synthesis/` 争议页
3. **诚实标注**：来源等级（A/B/C）、语言来源、样本缺失，全部写在文件里

## STEP 8.5 — 聚焦子区采集（选题落在已有专题区内时）

当用户的问题**范围更窄但更有指向性**（例：在「某地区发展」专题里问「**前十名**」），
**不要新开一个平级专题区，而是在已有专题区内开「聚焦子区」** —— 父区答「怎么做」，子区答「**谁做得最好、模式有何不同**」。

```
raw/<专题>/
├── index.md
├── zh-CN/ zh-TW/ ja/ en/ bilingual/    ← 语种目录（横向切分）
└── <聚焦子区>/                          ← 命名用问题主题，如 china-top10/
    ├── index.md                        ← 榜单依据 + 横向对比矩阵 + 模式分型 + 口径分歧 + 补源优先级
    ├── YYYY-MM-DD_<对象1>-<主题>.md     ← 每个对象一份，结构统一（定位/数据/机制/代表/模式/争议）
    ├── YYYY-MM-DD_<对象2>-<主题>.md
    └── ...
```

**单对象文件的统一骨架**（保证横向可比）：
`一、定位 → 二、关键数据（表格，逐年/逐指标）→ 三、核心机制（分 1/2/3 条）→ 四/五、载体与代表 IP → 六、模式解读 → 七、争议与不确定性 → 交叉引用`

> 子区内的文件**互相交叉链接**（「对比阅读：X · Y」），并在 `index.md` 提供对比矩阵 —— **这是子区相对散篇的价值所在**。

### ⚠️ 榜单 / 排名类采集的纪律（不可违反）

排名是最容易被伪造的知识形态。**必须照做**：

1. **三源并列**：至少找 **2–3 份公开发布的榜单**，列出「发布机构 / 时间 / 评估口径 / 结果」四列。
   （例：产业视角指数 = 某尺度 16 城；省级文化产业指数 = **省级**尺度；竞争力十佳 = **资源**视角 → 三者前十几乎不重叠。**这个不重叠本身就是核心发现**。）
2. **绝不虚构排名**。找不到榜单就明说「无公开榜单，以下为按 X 指标自建排序」。
3. **自建名单必须显式声明为「复合判断」**，写清依据（交集 / 规模数据 / 模式辨识度），**不得伪装成某榜复印**。
4. **口径不可横比就标注不可横比**。最常见的坑：
   - 「细分赛道口径」vs「全口径」—— 可差数倍，**媒体常直接横比，属误用**；
   - 「核心领域营收」vs「新业态规上企业营收」—— 可差数倍；
   - 名义增速 vs 可比口径增速（后者是统计局可比口径并注明规上范围每年变化）。
   → **处理方式：并列保留两处，标注口径差异，不换算、不取平均、不择一。**
5. **数据空白如实留空**。若某对象**没有公开的产业数据**（如仅有客流/社零），**明写「未检索到，本文留空」**，
   并把 `confidence` 降为 `medium`。**严禁用替代指标冒充**（不得用客流量替代产业营收）。
6. **为每个对象写「争议与不确定性」**，并给出**补源优先级**（哪个数字最该被第三方核验）。

> **反面示范**（不要做）：给一个漂亮的排名表 → 不写机构不写口径 → 把不同口径的数字排在一起 → 缺数据的对象用别的指标凑 → 看起来完整，实则全部不可核验。

## STEP 8.6 — 同母体多城 / 同源对象对比子区（选题是「同一母体的 N 种路径」时）

**识别信号**：用户给出一组**共享同一文化母体**的对象，问它们的资料（例：「某文化特色的甲、乙、丙三地的市场与产品内容」「同一条河沿岸的三个古镇」「同一剧种的三个院团」）。
这类选题与 STEP 8.5 的「谁最好」**本质不同**——它问的是「**同源为何不同路**」。

### 结构（四件套，缺一不可）

```
raw/<专题>/<子区>/
├── index.md                                  ← 文化资源逐项对比 + 模式分型 + 口径分歧 + 可迁移模式排序
├── YYYY-MM-DD_<母体>-(cultural|shared)-<matter>.md   ← ① 母体制度页【必建】
├── YYYY-MM-DD_<对象1>-<主题>.md                        ← ② 每对象一份城市/单页
├── YYYY-MM-DD_<对象2>-<主题>.md
├── YYYY-MM-DD_<对象3>-<主题>.md
├── YYYY-MM-DD_<横向问题1>.md                          ← ③ N 份跨城专项
├── YYYY-MM-DD_<横向问题2>.md
└── ...
```

**① 母体制度页是前提，不是可选项**。不写清「这些对象为何共享同一批素材」（行政制度 / 语言 / 建筑体系 / 剧种 / 信仰 / 侨乡网络 / 交通走廊），**横向对比就没有合法性**。
- 母体若是一份**国家级制度**（如国家级文化生态保护区），把它的**范围、理念、法治工具、阶段规划**写清楚，并对比各对象在同一制度下的**差异化落地**（例：甲地做「建筑 + 传习所网络」，乙地做「品牌活动 + 传承人补助」）。
- 母体页应给出**「制度底座如何转化成产品」的机制链条图**（合法性与资金 → 传承人 → 活态场景 → 数字素材库 → 产品）。

**② 每对象单页骨架**（与 STEP 8.5 一致，保证横向可比）：
`定位 → 关键数据 → 核心驱动力（分 1/2/3 条）→ 载体与代表 IP → 产品化路径 → 政策工具 → 模式解读 → 争议与不确定性 → 交叉引用`

**③ 跨对象专项是这类子区的灵魂**。**每份专项回答一个横向问题**，而不是纵向介绍一个对象。好的专项题：
- 某个**母体资源**如何被各对象分别产品化（例：建筑元素 / 同一份档案 / 同一门手艺）；
- 某个**现象级单品/项目**的完整拆解（例：一个爆红项目的「引爆—融合—传播」三段机制）；
- 某条**外向通道**（跨境 / 出海 / 区域联动）的三种机制对比；
- 某类**内容资产**（剧种 / 方言 / 方言内容）的产品化路线。
→ 专项文件内**必须逐项对比各对象**（表格），并明确指出**哪些元素已被产品化、哪些尚未被利用**（后者是本库标注的「机会点」，对用户最有价值）。

**④ index.md 的必备板块**：
1. 为什么这些对象必须合起来看（**列共享证据**：同一款产品联动两地资源 / 同一批元素被两地使用 / 同一份档案被三地做成三种产品）；
2. 总览对比表（维度 × 对象）；
3. **母体资源逐项对比**（资源 / 街区 / 工艺 / 内容 / 建筑 / 记忆遗产……每项一节，多对象并列）；
4. **模式分型**（按「**营收主体类型**」分，而非按行政级别或名气）；
5. 与已有子区的分型**对照说明**（重叠与差异，并列保留不强行统一）；
6. 口径分歧表（**并列保留，不取折中**）；
7. 共同核心张力（2–5 处，必须写「**官方提出但未回答**」的问题）；
8. **可迁移模式排序表**（★ 数量标可迁移性，每条注明出处）—— 这是最受用的产出；
9. 来源质量分级 + 补源优先级。

### 模式分型的判据（关键）

**按「营收主体是谁」分型**，不要按名气或行政级别。同一个母体下常见三型：

| 型 | 驱动内核 | 判据（看这个） |
|---|---|---|
| **技术/平台型** | 数字内容企业 + 国家级平台 | 文化科技对增长贡献率、高企数量、出口榜单 |
| **制造/产业带型** | 规上制造业企业 + 县域「一县一品」 | 规上企业数、集群规模、版权登记量 |
| **运营/模式型** | 街区运营模式 + 景区 | 单位模式营收、可复制模式数量 |

> **若分型暴露出已有框架的盲区，必须明确指出并建议扩充框架**。
> （例：某子区发现「制造业驱动型」在其父区的城市分型中完全缺失 → 应显式提出「建议纳入第 N 种模式」，并说明它与既有类型的判据差异。）

### ⚠️ 语言诚实标注（强制，不可违反）

这类子区极易碰到主权相关表述。**必须照做**：

1. 涉及**中国台湾 / 中国香港 / 中国澳门**时，统一表述为「**中国台湾**」「**中国香港**」「**中国澳门**」，或「中国台湾地区」「香港特别行政区」等；**绝不表述为独立国家**。
2. 引用来源原文（如「台湾地区主题馆」「台青」「金门馆」）时，在**本库自身表述**中做对应转换；**历史文献名原样保留**（如《续修台湾府志》），必要时加注「史料名称」。
3. 涉及主权与领土完整的表述，**以国家立场为准**（如金门按国家立场表述为**中国福建省金门县**），**客观记录文化交流事实，不作政治化延伸**。
4. 该类子区**在 AGENTS.md 第 7 节写明这条规则**，使后续所有会话都受约束。

## STEP 8.7 — 企业方向采集（选题从「政策/政府」下沉到「企业主体」时）

**识别信号**：用户说「现在收集的都是政策方向以及政府方面的资料，接下来请**下沉**收集**企业方向**的内容、资料以及产品」，
或直接点名要「企业/品牌/公司层面」的产品、内容、财务数据。

### 先确立「三区主语分工」（这一步决定整个区怎么写）

`raw/` 下多个专题区并存时，**每个区的主语必须不同**，否则内容会互相污染：

| 区 | 主语 | 回答的问题 |
|---|---|---|
| `raw/regions/` | **政府** | 城市/政府**怎么组织** |
| `raw/enterprise/` | **企业** | 企业**怎么落地、怎么赚钱** |
| `raw/methods/` | **创作者** | 方法/创意**怎么做出来** |

> 建档时**第一件事**就是把这个分工写进 `AGENTS.md` 与区索引。它是防止「企业区越写越像政策区」的唯一保障。

### 结构（四类并列，缺一不可）

```
raw/enterprise/
├── index.md          ← 汇总：企业矩阵 + 核心发现 + 横排纪律 + 质量分级 + 补源优先级
├── brands/     (N 篇) ← 企业单页【一家一页】
├── content/    (N 篇) ← 内容策略专项【IP 内容生态 / 联名与授权 / 社媒与内容电商】
├── products/   (N 篇) ← 产品专项【产品解剖 / 价格带与材质 / 供应链与代工】
└── data/       (1 篇) ← 企业财务与经营指标横向矩阵（含口径分歧辨析）
```

**为什么必须四类并列**——因为用户说的「内容、资料、产品」正好对应后三类，而「资料」的落点是**企业单页 + 数据矩阵**。
只写企业单页会漏掉产品与内容；只写数据会没有故事。

**企业单页骨架**（先与用户对一下：这一家的**报告期**是哪一年）：
`年报核心数据 → 产品结构 → IP 矩阵 → 渠道与用户 → 分区域 → 非主营业务（内容化） → 战略与组织 → 争议与不确定性 → 对本库的价值 → 交叉链接`

### ⚠️ 企业数据纪律（强制，本区特有）

1. **凡经营数据必须写明报告期与口径**（「2025 年度年报」/「2025 财年 2024.4–2025.3」/「招股书申报稿」）。
2. **同一公司不同披露口径冲突时并列保留**，并**尽量算出差异的可核验机制**，而不是只说「口径不同」。
   - 范例（可复用）：某子公司出现「独立招股书 X 亿」与「母公司财报分部 Y 亿」两个数。
     算一遍：X − 向母公司关联销售 = Y（近似），再验上一年同样成立。
     → **差异 = 关联交易剔除，两个数字都对**。这一步把「口径不同」升级为「口径已解」，是本区最有价值的动作。
3. **集团分部口径 ≠ 子公司独立口径**，不得直接横比。
4. **未上市公司以招股书为准**，并标注「申报稿，可能更新」。
5. **横排纪律**（写进索引的必备板块）：报告期不同不可混排名 · 会计口径须标（A 股 vs IFRS）· **净利须标报表口径还是经调整口径** · 申报稿 ≠ 审计数据 · 海外数字为媒体汇率折算时须标汇率。

### 本区能挖到的 5 类高价值发现（按经验排序）

1. **毛利率阶梯 ≈ IP 归属阶梯** —— 把「代工厂毛利 X% / 生产端 Y% / 集合店+第三方 IP / 授权 IP+自研 / 大众零售+IP 联名 / 授权+自有自研 / 自有 IP 主导」串成一条链，
   用各家**年报毛利率**填进去。⚠️ **但必须检查例外**（例：某标准化品类的公司毛利率高于某自有 IP 更高的公司，因为**标准化生产 + 高复购**同样决定毛利）→ **有例外就只写成「倾向性规律」，不要写成公式。**
2. **「自研」≠「自有」** —— 中文语境下极易混淆的两个词。企业常宣传「**自研产品收入占比** XX%」，
   但其中大部分是**第三方 IP 授权后自行设计生产**；**真正自有 IP 收入占比**可能只有个位数。
   → **本库统一要求：涉 IP 归属必须写「自有 IP 收入占比」，不写「自研产品占比」。** 这是最容易抓到、也最容易被别人漏掉的一条。
3. **内容能力 ≠ 变现能力** —— 把「有自有长篇内容 IP 的公司」与「没有内容的头部公司」并列：净利润率可能相差 10 倍以上。
   → 若找不到原因，**写成一个明确标注「未验证」的假设**（例：内容排播以「年」为周期，而商品需每 IP 每年 3–6 个新系列，**节奏不同频**），不要下结论。
4. **规模增长与门店收缩可同时发生** —— 头部公司常出现「收入 +1XX% 而门店净增个位数」→ 说明**增长来自单店效率与线上**。
5. **价格带 × 材质的换算实证** —— 若能找到「零售价 X 元、销量 N 件、确认收入 Y 元」的一手数据，
   **算出「零售价 ÷ 厂端收入」的比例**（通常约 2 倍）。这是理解「企业营收 ≠ 零售额」的关键实证。
   ⚠️ 若只有**一个价位段**的样本，**必须标注「不可外推」**。

### 必备的「反向证据」板块

企业区最容易被写成企业宣传稿。**必须主动去找反向数据**，并单列一节：
- 门店倒闭/关店数、行业闭店率、同质化比例（多少家店卖相同 IP）、行业集中度（CR5）；
- 二手市场价格崩塌案例（高价 → 按斤称）；
- 企业自陈风险（招股书的「风险因素」章是最诚实的材料来源）；
- 「上新—滞销—打折」这类**恶性循环**的警示性判断。

### 数据来源优先级

| 级 | 类型 | 写法 |
|---|---|---|
| **A** | 年报 / 招股书 / 业绩公告（经财经媒体转述亦可） | 标 `source_grade: A` |
| **B** | 权威财经媒体（证券时报、中国证券报、新华财经、党报系） | `source_grade: B` |
| **C** | 行业平台 / 二手汇编 / **代工厂与厂商自述页** | `source_grade: C`，并在文件内**显式区分哪些参数可商用、哪些仅作量级参照** |

> **⚠️ 厂商自述页的处理（经验教训）**：查供应链参数（打样周期、MOQ、良品率、报价）时，搜索结果**大量是代工厂的推广稿**。
> **不要丢弃**，但必须**分类标注**：把「党报系报道的产业数据」与「代工厂自述的工艺参数」在同一页内**分表列出**，
> 并写明「采购决策请以实厂核验为准」。**这比删掉它们更有用**（用户确实需要量级参照）。

## STEP 8.8 — 爆款/单品史聚焦子区（选题落在「哪些产品爆了、怎么演化过来的」时）

**识别信号**：用户说「在**产品层面**，分析和收集这几年**爆款**的几种产品，分析一下该产品**发展的过程**」，
或直接点名要「爆款盘点 / 历代爆款 / 产品演化史 / 产品代际」。

**不要新开平级专题区** —— 在已有多类目专题区（如 `raw/enterprise/`）内开**聚焦子区 `hits/`**。

### 先确立「横切 vs 纵切」分工（决定整个子区怎么写）

| 目录 | 视角 | 回答 |
|---|---|---|
| `products/`（已有，横切） | **横切** | 一个产品**由什么构成**（系列结构 / 材质 / 价格带 / 供应链） |
| **`hits/`（新建，纵切）** | **纵切** | 哪些产品**爆了**、怎么演化、怎么退场 |

> **同一事实只在一处展开，另一处引用。** 这是防止「新子区把旧的产品页重写一遍」的唯一保障。
> 建档第一件事就是把这个分工写进 `AGENTS.md` 与区索引。

### 结构（固定八件套，缺一不可）

```
raw/<专题>/hits/
├── index.md                          ← 汇总：核心发现 + 数据纪律 + 冲突表 + 来源分级 + 补源优先级
├── YYYY-MM-DD_five-generations-evolution.md      ← 【主文】产品代际演化论 + 规律 + 完整时间轴
├── YYYY-MM-DD_hit-<category1>.md                 ← 品类爆款页（一品类一页）
├── YYYY-MM-DD_hit-<category2>.md
├── ... (6 份品类页为宜)
└── YYYY-MM-DD_hit-lifecycle-hype-curve.md        ← 【规律页】生命周期与溢价曲线
```

**为什么是「1 主文 + 6 品类 + 1 规律」**：
用户说的「**几种产品**」对应 6 份品类页，「**发展的过程**」对应主文 + 规律页。
只写品类页会没有演化叙事；只写主文会没有单品数据。

**品类页的选择原则**：按**用户所在市场的实际货架**切分，不按学术分类。
（示例：某消费品类的六分——A 类 / B 类 / C 类 / D 类 / E 类 / F 类，
注意某两个看似相近的子类实为不同赛道，**不可合并**。）

### ⚠️ 二级市场数据纪律（强制，本类子区特有）

爆款页**必须**同时满足三条，否则会变成「小红书式爆款文」：

1. **溢价必须标注是「报价」还是「成交」** ——
   搜到的「原价 X 元炒到 Y 元」几乎都是**挂单价**。若全为报价，须在文件内明写
   「本页溢价数据均为报价，唯一可参考成交记录为 X」。
2. **同一商品的价格区间必须完整保留，不归并、不取中位** ——
   实测同类商品在**同一周内**出现数倍到十几倍的报价。
   **那不是「市场价格」，那是「报价分布」。**
3. **币种必须判定并标注** —— 跨境媒体转述极常见多币种混用。
   实测同一场拍卖被写成「落槌 A 万元」与「拍出 B 万天价」，
   经验算「A 万 × 约 N ≈ B 万」判定为**同一事件的另一币种折算**。
   → **以一手来源币种为准，并写出折算依据**，不要改掉原来源数字。

### 必备的「反向证据」板块（爆款页最容易被写成企业宣传稿）

每份品类页须单列，**主动去找**：
- 盗版规模（如「盗版商品销量超 10 万件」）；
- 闭店数 / 关店率（如「上半年 155 家闭店、新开店 14% 未撑过一年」）；
- 价格崩塌案例（如「高价 → 按斤称」）；
- 质量瑕疵（如「正版商品因赶工出现瑕疵」）；
- 同质化比例、行业集中度。

### 本类子区能挖到的 4 类高价值发现（按经验排序）

1. **每一代爆款，都是上一代护城河失效后找到的新护城河** ——
   把各代爆款的「护城河」和「它为何失效」成对列出，得到一条**防御史**而非进步史。
   ⚠️ **要找因果起点**（例：某公司失去代理权 → 该品类占其门店营收 1/3 → 被迫转自有 IP），
   起点往往比过程更有解释力。
2. **爆款生命跨度相差可达近 90 倍，取决于稀缺性来源** ——
   把各爆款的**峰值持续期与爬坡期**放同一时间尺度上对照。
   **人为制造的稀缺（限量/概率/产能）会随供给追平而崩；天然存在的稀缺（文物唯一性）不会。**
3. **溢价 ≈ 需求峰值 ÷ 供给弹性**（可写为主文推测公式，**必须标注「未验证」**）——
   用「供给约束类型 × 溢价倍数」列表支撑。**若无成交价序列，须明写公式无法验证。**
4. **修正「内容能力 ≠ 变现能力」** —— 该发现需细化为
   **「内容的价值不来自有没有，而来自内容本身是否成为爆款」**
   （例：有强内容且内容爆了的作品衍生品从 1.2 亿 → 100 亿；而多个顶流 IP 完全无叙事支撑）。
   ⚠️ **发现修正后要回写父区索引**，并在父区的旧表述旁加「已被后续采集修正」注。

### 本期易踩的两个坑

| 坑 | 现象 | 对策 |
|---|---|---|
| **同母题数字跨币种被当成两个值** | 同一场拍卖被写成「A 万元」与「B 万」 | 先做**折算验算**再判定，**不要并列成两个独立数字** |
| **名单与数字自相矛盾** | 媒体写「6 个 IP 超 20 亿」并列出 6 个，但其中一个实为 17.35 亿 | **以数字为准，判定名单表述有误**，并在「争议」中写明 |

### index.md 的必备板块

1. 八件套清单表（文件 / 类型 / 内容 / 来源级）；
2. **4 个核心发现**（每条给一句可引用的一句话证据）；
3. **本区数据纪律**（继承父区横排纪律 + 本类新增的二级市场三条）；
4. **并列保留的全部数字冲突表** —— 这是本类子区公信力的核心；
5. 来源质量分级（标注哪几篇含一手财报数据）；
6. 补源优先级（**二级市场成交价**与**市场规模口径统一**通常排前两位）；
7. 交叉链接（父区 / 横切的 `products/` / 相关企业单页 / 上游创意区）。

## STEP 8.9 — 过程思考落盘（用户要求「把有用的思考 / 推理过程也保存下来」时）

### 为什么必须做（先说清价值，否则一定写成流水账）

`raw/` 保存的是**结论 + 来源**，但**推理路径只存在于对话中**——会话一压缩就丢。后果三条：

1. 同类数据冲突下次要从零推一遍；
2. **已证伪的旧判断会被后来的读者重新当作结论引用**；
3. 页面标 `confidence: medium` 时，**依据无从复核**。

→ 因此 `reflections/` 分**两类，不要混**：

| 类别 | 回答的问题 | 命名 |
|---|---|---|
| **决策记录（ADR）** | 「我们决定怎么做，为什么」 | `YYYY-MM-DD_<topic>.md` |
| **过程思考落盘** | 「**这个判断是怎么想出来的**」 | `YYYY-MM-DD_<topic>-reasoning.md` |

### 触发条件（默认不落盘）

- 用户明确指令「记下 / 保存 / 归档」→ 写；
- 一轮工作产生**可复用的推理模式**、或**推翻了本库既有判断** → **主动询问**是否落盘（**不擅自写**）。

### ⚠️ 筛选判据（关键：不是所有中间推理都值钱）

**算「有用的过程思考」（满足任一即候选）：**

1. **可复用的推理模式** —— 面对同类数据冲突通用的判定动作；
2. **被证伪并修正的判断** —— 含旧表述如何保留；
3. **口径冲突的解决路径** —— 从「并列」升级为「算通」的过程；
4. **取舍决策及理由** —— 为什么这样切分、为什么否决另一方案；
5. **反事实推演** —— 「否则不会发生」的那个瞬间；
6. **分类轴的更换** —— 旧轴解释不了差异时换的新轴。

**不算**（这些属于 `.kb/memory/` 工作记忆，不进 reflections）：
一次性的中间搜索结果 · 临时文件路径 · 工具报错 · 逐步执行日志 · 未成形的零散想法。

### 每篇必含三样（缺一不可）

1. **「为什么单独落盘」** —— 它可复用在哪；不写就退化为随笔；
2. **推理动作分步** —— 记录每一步做什么、为什么这样走，**而不是只给结论**；
3. **「适用边界」** —— 这条推理什么时候**不成立**。

### 🚨 两条强制纪律

- **诚实分层**：区分「**硬数据 / 强推断 / 本库建构或推测**」三层，推测须在**首次出现处标注「未验证」**；
- **修正留痕**：推翻旧结论时**不回删旧表述**，在原处加**修正注**并指向新页 —— 知识库的价值不只在当前结论，也在**结论怎么变的**。

### frontmatter

```yaml
type: reflection
title: "..."
description: "..."
tags: [reflection, reasoning, ...]
status: final
timestamp: ...
reasoning_for: ...   # 可选：本页推理链所服务的主题 / 来源页
```

### 同步动作（别漏）

`AGENTS.md` 新增约定 → `okf.yaml` 的类型描述与 `extended_fields`（`reasoning_for`）→ `reflections/index.md` 重写为**两类结构** + 写作要求 → `index.md` 统计 → `log.md` → memory。

> **实战范例**：`reflections/YYYY-MM-DD_<topic>-reasoning.md`（**口径辨析的推理模式**）与 `YYYY-MM-DD_<topic>-reasoning-chain.md`（**某专题的演化推导链 + 一处假设被自我证伪的完整记录**）。

## STEP 8.10 — Compile 产出（用户要「一份成稿 / 报告 / 手册 / 决策备忘」时）

**先分清 Compile 与 Ingest**——这是最容易混的一步：

| | Ingest | **Compile** |
|---|---|---|
| 方向 | raw → wiki | **wiki → results** |
| 产物 | 可复用的概念页 | **一次性成稿（交付即定稿）** |
| 何时做 | 来了新来源 | 用户要**能直接给人看**的东西 |

**三条纪律（强制）**：

1. **必须引用已有 wiki 页** —— 成稿是"编译"不是"新写"；`sources` 字段须列出所用 wiki 页与 raw 页；
2. **必须复述口径与 `confidence`** —— **交付物不得比来源页更"确定"**（把 `medium` 写成"已证实"是最严重的违规）；
3. **交付即定稿**（`status: final`）—— 不再迭代；如需更新**新建版本**，不改旧文件。

**推荐结构（"决策手册"式七段，比"研究报告"式更有用）**：

```
① 三分钟读懂（定义 + 价值链 + 大盘锚点 + 域地图）
② N 个关键判断（每条：判断 → 依据 → 谁能用）
③ 逐域速览（每域一页纸：核心逻辑 / 数据 / 机会 / 风险）
④ N 条可执行原则（每条：动作 → 依据 → 边界）   ← 最有价值的一段
⑤ 数据使用纪律（口径铁律 + 检查表 + confidence 分级）
⑥ 附录：本库地图
⑦ 附录：本库明确的未解问题（诚实边界）
```

**关键**：**第 ④ 段是成稿与 wiki 的分水岭。** wiki 给"知识"，成稿给"动作"。缺乏动作段落的成稿只是 wiki 的复制粘贴。

> **实战范例**：`results/YYYY-MM-DD_<title>.md`（七条可执行原则 + 数据纪律，`status: final`）。

## STEP 8.11 — 把「诚实标注」变成可复核动作（confidence 标准 + 企业数据口径）

`confidence` 若只凭直觉标注，等于没有标准。**落两个页把直觉固化为动作**：

### A. `metrics/confidence-levels.md` —— 四维判定（取最低值）

| 维度 | high | medium | low |
|---|---|---|---|
| ① 来源级别 | A（披露本体/官方统计/政策原文/论文） | B（权威媒体/研究机构） | C（行业转述/厂商自述） |
| ② 口径明确性 | 口径+报告期+统计对象**三者明确** | 其一需推断 | 至少两项不明 |
| ③ 多源互证 | ≥2 独立源同向 | 单一源 | 多源冲突无法解释 |
| ④ 结论类型 | **数据型** | 强推断 | **本库建构 / 推测** |

**两条硬规则**：**① 单一来源不构成 high**（除非该来源本身就是该指标的权威统计本体）；**② 维度 ④ 是硬上限——本库建构的结论最高 `medium`，纯推测最高 `low`，无论来源多好。**

- **升级到 high** 的五个必要条件（含"能直接溯源到原始披露"）
- **降级触发**（发现同口径冲突 / 原 A 级实为申报稿 / 结论实为本库归纳 / 报告期不统一被横排 / 厂商自述被当独立事实 / 数量级疑汇率）
- ⚠️ **`status` ≠ `confidence`**：前者是编辑进度，后者是可信度；一页可以 `status: stable` 但 `confidence: low`

### B. `metrics/enterprise-financial-metrics.md` —— 企业财务九项检查表

引用任何企业数字前逐项过：

```
□ 集团 / 分部 / 子公司 哪个层级？   ← 跨层级比较是错误
□ 报告期？（财报年 / 自然年 / 混合决算期）
□ 会计口径？（CAS / IFRS / 日 GAAP / US GAAP）
□ 利润口径？（报表 / 经调整）
□ 市占率口径？（GMV / 零售额 / 营收）
□ 价格口径？（出厂价 / 零售价）
□ 申报稿还是审计数据？
□ 是否含政府补助等一次性项？
□ 汇率折算是否已标？
```

**九项全过 → 可标 `high`；缺 1–2 → `medium`；缺 3 以上 → `low`。**

**两个必记的实证坑**：① **集团分部口径 ≠ 独立主体口径**（某子公司独立报表经营利润为正，集团分部口径为负，**符号相反**）；② **混合决算期**（某母公司 4–3 月 + 海外子公司 1–12 月 → 任何同比都混入结构变化）。

> **实战范例**：`wiki/metrics/confidence-levels.md` 与 `wiki/metrics/enterprise-financial-metrics.md`。

## STEP 9 — 收尾

1. **回填统计**：手写的 `index.md` 统计表要与 `build_index.py --stats` 的实际数字一致
2. **写 `log.md`**：`## [YYYY-MM-DD] init | 项目初始化` + `## [...] lint | 初始化健康检查`
3. **写 `.kb/memory/`**：`MEMORY.md`（长期）+ `YYYY-MM-DD.md`（当日日志）
4. **写 `reflections/YYYY-MM-DD_<project>-architecture.md`**：架构决策记录（ADR），记录
   **为什么这么设计**、**否决了哪些方案**、**遗留问题**；
   - 若本轮产生了可复用的推理模式或推翻了既有判断，另写 `YYYY-MM-DD_<topic>-reasoning.md`（**过程思考落盘**，见 STEP 8.9）
5. **若本轮做了 Compile**：写 `results/YYYY-MM-DD_<title>.md`（`status: final`）并更新 `results/index.md`；若此前无 Compile 约定，须在 `AGENTS.md` 补一节（触发条件 + 三条纪律）
6. **展示成果**：README.md / AGENTS.md / index.md / wiki/overview.md / **results 成稿（若有）** / ADR（或过程思考页）

## 内容质量要求（容易被忽略）

- **不要把每页写成百科摘要**。每页至少要有：定义 → 机制/数据 → **争议与不确定性**
- **数据必须双源并列**。同一指标不同来源冲突时，列**对照表**并说明为何冲突（口径/基期/范围）
- **主动标注数据缺口**。缺什么指标、为什么重要、去哪里补 —— 这比编数字有价值
- **`confidence: low` 不是失败，是诚实**。宁可标 low 也不要假装确定
- **每页结尾"交叉引用"小节**列出 2-5 个相关页，保证无孤儿页
